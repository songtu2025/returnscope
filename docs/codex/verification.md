# Codex 验证与完成报告规范

制定验证方案、执行检查、判断完成状态或输出完成报告时，必须读取本文件。

## 1. 项目检查声明

项目 README 必须记录实际可执行的 Windows 和 Linux/CI 检查命令。命令可以不同，但必须覆盖相同能力；本规范不限定脚本名称和任务运行器。

检查命令不得安装依赖、修改文件或静默跳过必需检查。优先使用项目统一入口，否则按实际配置逐项执行。根目录 README 已记录 Windows 和 Linux/CI 的统一检查入口；README 与实际配置不一致时必须先修正，不能据此省略检查。

## 2. 结果状态

每项检查只能报告为：

- **通过**：命令实际执行且退出成功。
- **失败**：命令实际执行但未通过。
- **未配置**：受影响模块缺少必需命令或工具，不能标记完成。
- **不适用**：任务不影响该模块，或项目不存在对应能力；必须说明原因。
- **未自动验证**：缺少自动化工具但已进行人工检查；必须说明方法和局限。

## 3. 最低验证能力

任务影响前端时必须覆盖：

- 格式检查。
- ESLint。
- 与当前 JavaScript/JSX 对应的类型或静态分析；没有配置时报告为“未配置”。只有任务涉及 TypeScript 时才要求 TypeScript 类型检查。
- 自动化测试。
- 生产构建。
- React、Phosphor Icons 和 Recharts 的版本兼容性、重复安装及第二套 UI 或图标依赖检查。

任务影响后端时必须覆盖：

- Ruff 格式和静态检查。
- 项目选定的 Python 类型检查器。
- pytest。
- 任务涉及数据库时执行 `app_migrations`、备份、回滚和生产数据搬运的相关测试；本项目不执行 Alembic 检查。

存在相应配置时还必须覆盖 Docker Compose 配置和禁止提交文件检查。缺少必需命令或工具时不得静默跳过。

## 4. 任务专项验证

新增、修改或评审代码时，还必须使用项目已有工具检查：

- 本次涉及文件的职责和规模。
- 函数圈复杂度、认知复杂度、分支数、语句数、嵌套和参数数量。
- 代码重复、死代码和循环依赖。
- 源码和提交记录中的敏感信息；扫描结果不得显示真实命中值。

项目缺少相应工具时，不得擅自增加生产依赖；应进行人工检查，并在完成报告中列为“未自动验证”。人工检查不能伪装成自动化检查通过。

涉及界面时，必须按 `docs/web-ui-standard.md` 及任务命中的专项规范验证目标视口、页面状态、键盘路径、焦点、对比度、溢出和横向滚动。

本项目还必须确认现有自定义主题生效，主要业务图标来自 Phosphor Icons，图表使用 Recharts；Ant Design 只用于已确认的模块与控件范围，且没有重复安装、二次封装、第二套 UI 组件库或第二套主要图标体系。

### 4.1 规模、测试与数据

按 `docs/codex/code-quality.md` 核对代码文件的物理行数：新增文件超过 300 行，或原本不超过 300 行的文件本次修改后超过 300 行时，不得标记完成；既有超限文件仅作存量提醒，必要的局部修复不因此失败，触及时报告行数和建议的优化时机。函数指标须区分工具检查与人工审查结果。

新增测试文件时，核对该模块是否尚无对应测试文件，或是否需要独立测试模块、拆分混杂职责；已有文件可用时不得因任务变化另建文件。行为变更或测试清理后，核对旧测试的去留与当前要求一致；合并、删除测试时运行受影响测试，确认必要场景仍有覆盖，不得通过删除有效的失败测试取得通过结果。

新增或变更持久化数据结构时，还须核对业务对象与约束设计、索引依据、模型与迁移一致性；在隔离测试数据库验证升级，以及适用的降级或恢复方案。涉及数据约束或一致性规则时，用测试覆盖相应行为，不得使用真实业务数据验证。

### 4.2 API、权限与文件

新增或修改 API 契约时，还须核对请求、响应、校验、错误结果和权限要求与实际接口一致；验证受影响的成功和失败场景。涉及前后端共同变更时，核对前端调用与接口契约一致；已有调用方受影响时，验证兼容或迁移方案。不适用的检查点说明理由。

列表接口允许客户端指定页大小时，直接验证超出上限的输入按接口约定处理；允许指定排序字段时，直接验证未允许的字段按约定处理。不要求所有列表使用相同上限。

涉及前端公共请求处理时，验证受影响的认证状态、超时和通用错误反馈，并确认业务特有错误仍能正确处理。涉及 API 错误契约时，验证受影响的错误类别可被调用方区分，且对外结果不泄露内部或敏感信息。

涉及权限、业务规则、数据范围或关键计算时，还须直接调用受影响的 API，验证绕过前端后校验和权威结果仍然成立；前端的隐藏、禁用、即时提示和本地计算不能替代此项验证。

已有认证的项目新增或变更匿名接口时，直接验证未登录调用仅能获得预定范围的数据，并验证相邻的受保护接口仍拒绝未授权调用。

同一业务数据有列表、详情、统计或导出等多个入口且涉及访问规则时，直接验证受影响入口的数据范围一致，或与已确认的业务例外一致。新增审计要求时，核对必要字段和敏感信息排除；涉及导入、导出、上传或下载时，验证受影响的权限、范围和失败场景，导入或上传还须验证文件限制。

涉及导出时，用符合权限范围的测试数据核对导出字段和敏感字段处理方式。涉及私有文件下载时，直接验证未授权用户无法通过文件链接或下载接口取得文件，且有权用户能正常下载；公开文件按已确认的公开范围验证。

涉及批量导入时，还须验证重复记录处理、失败后的实际写入范围与已确认规则一致，且结果能区分成功和失败。涉及定时任务时，验证受影响的重复或并发执行、失败处理和执行结果记录；项目提供 OpenAPI 文档且接口发生变更时，核对生成文档与实际契约一致。

## 5. 需求、原型与 PDCA 专项验证

标准和高风险任务还必须核对：

1. 现有做法已区分业务规则、硬约束、工具限制和操作习惯，未将旧工具的补救步骤机械复制到目标系统。
2. `As-Is` 和 `To-Be` 已对保留、变更和删除的步骤说明理由，关键变化已获得用户确认。
3. 每个业务步骤有对应角色和规则，每个用户操作有权限、页面入口和结果反馈，每项数据有来源、去向和生命周期。
4. 页面、接口、数据和验收标准能追溯到明确的业务目标；不适用的设计视角已说明理由。
5. 使用 Demo 时，合成数据不包含真实敏感信息，界面已标识演示状态，且未将 Demo 通过误报为功能完成。
6. Demo 进入真实开发后，已先定义契约并打通至少一个真实端到端流程；未达到生产要求的 Demo 代码未被保留。
7. 有可观测业务效果时，基线、目标、指标、数据来源、负责人、复查时间和后续动作已明确；不适用时已说明理由。

## 6. 规范文件专项验证

新增、合并或升级 `AGENTS.md` 及其专项规范时，还必须检查：

1. 原有业务、架构、检查和禁止事项未因模板接入或精简而丢失。
2. 根规则、嵌套规则、`AGENTS.override.md` 和专项文档的作用域及优先关系明确。
3. 所有索引路径存在，并且每个索引都说明了准确的读取条件；未同步的专项规范没有残留索引。
4. 每条规则只有一个事实来源，没有冲突、失效或已由工具强制却仍逐条复述的内容。
5. 新项目根 `AGENTS.md` 不超过 100 行；现有项目超过目标时已说明原因和治理方式。
6. 适用的项目规则链未超过 Codex 当前配置的文档大小限制；接近限制时优先减少始终加载内容。
7. 项目 README 已记录公司规范基线版本、接入来源、接入日期、版本控制状态、加载验证、项目差异和真实检查命令。
8. 存在目录规则时，从代表性工作目录核对 Codex 实际加载的来源和顺序。
9. 新增规则有明确的问题、安全要求、平台限制、技术决策或验收需要作为依据。
10. 删除的规则已经失效、重复、由工具稳定强制或不再适用，并符合规范版本规则。
11. 接入前已确认业务项目根目录和规范来源；ZIP 在项目外处理，完整规范仓库未嵌套到业务项目。
12. 没有 Git 且修改已有规则文件时，目标规则文件已备份到项目外并说明恢复方法；完成报告未将临时备份表述为版本控制，也未声称已经提交或推送。
13. 适用文件已复制或合并到正确路径；新建 Codex 任务能够报告实际加载的 `AGENTS.md` 路径和关键规则。
14. 发布规范版本时，发布提交、README、CHANGELOG 和版本标签一致，且标签 ZIP 可以访问；非发布任务标记为不适用。

接入流程发生变化时，至少模拟以下情况：新项目无 Git 且网络正常；现有项目无 Git 且已有 `AGENTS.md`；GitHub 不可用而改用受控离线 ZIP；存在 `AGENTS.override.md` 或规则冲突。每种情况都须明确继续条件、停止条件和恢复方式。

## 7. 结果真实性与完成报告

完成程度必须按证据区分：

- **开发完成**：代码和适用的自动化检查通过。
- **交付完成**：真实数据或真实集成已验证，用户验收和发布条件满足。
- **闭环完成**：经过约定观察期，已根据业务指标做出保留、优化、回滚、暂停或下线决策。

尚未到复查时间时，只能报告“交付完成，业务效果待验证”，并列出指标、负责人和复查时间。简单且不存在持续业务效果的任务，闭环状态可标记为不适用。

完成报告固定为五项：

1. **结果**：需求和验收标准是否完成，并说明开发、交付或闭环状态；未完成时说明具体项目。
2. **修改**：修改文件、行为变化及新增或修改的测试。
3. **验证**：实际命令和结果状态，并包含代码健康检查；涉及界面时补充视觉、状态、键盘和可访问性结果。
4. **影响**：数据库、认证、权限、配置、依赖和部署影响，以及需要时的回滚方式。
5. **遗留问题**：失败、未配置、未自动验证、已知风险和后续动作；没有时填写“无”。

不得为了通过检查而删除测试、修改正确的测试预期、关闭检查规则、忽略类型错误、吞掉异常或隐藏失败结果。

只有满足验收标准、未超出范围、必要检查通过、未隐藏未验证内容且未降低代码健康度时，任务才可标记完成。代码已生成、能运行或理论可行都不等于完成。
