# Codex 代码质量与拆分规范

当任务新增、修改、重构或评审代码时，必须读取本文件。规则适用于所有进入仓库的代码。
## 1. 设计原则

1. 保持高内聚、低耦合，每个模块只承担清晰且相关的职责。
2. 保持依赖方向清晰，避免循环依赖和跨层调用。
3. 优先保证代码可读性，使用准确命名和简单控制流程。
4. 控制函数、类和组件的职责范围，复杂逻辑必须合理拆分。
5. 隐藏模块内部实现，仅暴露完成协作所需的最小接口。
6. 避免重复业务规则，但不得为了复用而过早抽象。
7. 优先遵循项目已有结构和实现方式，保持代码风格一致。
8. 代码设计必须便于测试、修改和问题定位。
9. 不得硬编码密码、密钥、服务地址、端口、文件路径和环境相关参数，应通过配置或环境变量管理。
10. 业务状态、类型、阈值和重复使用的固定值应定义为具名常量、枚举或集中配置，不得散落在代码中。
11. 仅当值含义明确、不会随环境或业务变化且只在局部使用时，才允许直接使用字面量。
12. 文件包含多个能够独立变化的职责，或已经影响理解、定位、测试和修改时，必须按业务边界拆分。
13. 拆分后必须保持依赖方向清晰和对外接口稳定，不得引入循环依赖、重复逻辑或无业务收益的文件碎片。
14. 维护历史长文件时只处理与当前需求相关的部分；大范围拆分必须先说明范围、收益和风险并获得确认。

## 2. 规模、复杂度与拆分

可维护性取决于职责、依赖、复杂度和可测试性。代码文件按物理行数计算，包含空行和注释；规则适用于源码、测试、配置及提交的生成代码，不包括文档、锁文件和第三方依赖。

1. 新增代码文件不得超过 300 行；原本不超过 300 行的文件，本次修改后也不得首次超过 300 行。预计超限时应先按职责设计拆分，不得通过压缩格式或删除必要的注释、测试规避上限。
2. 原本已超过 300 行的文件属于存量提醒，不阻塞无关任务或必要的局部修复。修改这类文件时报告行数、风险和建议的优化时机，由用户决定何时专项治理；本次不得加入无关职责，独立新能力应放入符合上限的模块。
3. 模块、类、组件或函数包含多个独立变化的职责时，按业务边界拆分；即使未超行数，也不得保留混杂职责。
4. 函数只完成一个明确目标。超过 50 行时检查职责与复杂度，不得仅为缩短函数提取无业务含义的辅助函数。
5. 函数的人工审查阈值为：圈复杂度 10、认知复杂度 15、分支数 12、语句数 50、嵌套块 5、位置参数 5。超过阈值时先简化流程、拆分职责或调整数据结构；仍需保留时说明原因。项目已配置的自动检查必须通过，不能用说明代替。
6. React 页面和组件分别检查数据获取、界面状态、表单、弹窗、表格配置和页面区域；混合多个独立职责时必须拆分。自定义 Hook 只封装内聚且可复用的状态或副作用，不得整体搬移复杂逻辑以规避检查。
7. 拆分后不得产生循环依赖、重复规则、空壳转发层、过度参数传递或难以追踪的文件碎片。
8. 单次变更新增和修改接近或超过 1000 行时，优先拆为可独立验证的阶段；无法拆分时，实施前说明原因并获得确认。
9. 功能修改与大范围重构原则上分开；重构是需求前提时，说明范围和回归风险。局部需求不必一次性治理全部遗留代码，但新增和修改不得降低代码健康度。
10. 完成后检查涉及文件的职责、规模和函数复杂度，报告预警、处理结果和未处理原因。

## 3. 注释与清理

注释应解释业务规则、设计原因、边界条件、特殊处理、兼容性要求和风险原因，不得简单重复代码含义。

完成任务后必须：

1. 检查本次新增代码是否重复已有实现。
2. 删除因本次修改而失效的旧代码。
3. 删除不再使用的 import、export、函数、组件和依赖。
4. 不得为了兼容“可能未来使用”的逻辑保留无实际用途的代码。
5. 使用项目已有工具检查代码重复、死代码和循环依赖；缺少工具时进行人工检查并如实报告。

## 4. 测试文件维护

测试文件按被测模块或业务域组织，不按任务编号、修改次数或日期新建。修改现有行为前先查找对应测试，优先更新或扩展原文件；该模块尚无对应测试文件、新增独立被测模块，或现有测试文件职责混杂需要拆分时，才新建文件。不得通过拆成零散文件规避 300 行上限。

行为变更后检查相关旧测试：仍验证当前要求的保留，预期变化的更新，重复的合并，只验证已移除行为且不再保护有效要求的删除。合并或删除前须确认必要场景仍有覆盖，之后运行受影响测试。不得仅因测试失败就删除仍有效的测试。
