# Codex 开发流程与项目边界

涉及代码、项目结构、配置、依赖、部署、项目文档或生产边界时，必须读取本文件。本文件与根目录 `AGENTS.md` 冲突时，必须先修正规则。

## 1. 技术与环境基线

公司新项目默认使用 React 18 及以上、TypeScript、Vite、Ant Design 6、FastAPI、SQLAlchemy、Alembic、Docker Compose 和 Nginx。现有项目以已经确认的技术栈和运行环境为准，不因默认基线迁移。

- 开发与代码托管：Windows、GitHub。
- 前端目录：`web-prototype`；React 19、JavaScript/JSX、Vite、自定义 CSS 组件、Phosphor Icons、Recharts。
- 后端目录：`web_backend` 及现有语义处理模块；Python、FastAPI、Pydantic、`sqlite3`、自定义迁移、pytest、Ruff。
- 部署入口：根目录 `Dockerfile`、`compose.yaml` 和 `Caddyfile`；使用 Docker Compose 和 Caddy。
- 界面范围：简体中文桌面 Web 运行驾驶舱，最低支持 `1024px` 宽，不承担移动端交付。

未经明确批准，不得迁移 Ant Design、TypeScript、SQLAlchemy、Alembic、Nginx 或其他框架、组件库、数据库访问方案和基础设施，也不得增加生产依赖。

## 2. 标准项目结构

新项目默认采用前后端分离、同一仓库管理的结构：

```text
project-name/
├── AGENTS.md
├── README.md
├── .env.example
├── .gitignore
├── compose.yaml
├── docs/
│   └── codex/
├── frontend/
│   ├── package.json
│   ├── src/
│   └── tests/
├── backend/
│   ├── pyproject.toml
│   ├── alembic.ini
│   ├── app/
│   ├── migrations/
│   └── tests/
├── deploy/
└── .github/
    ├── workflows/
    ├── ISSUE_TEMPLATE/
    ├── pull_request_template.md
    └── CODEOWNERS
```

新项目必须遵守：

1. 前端代码放在 `frontend`，后端代码放在 `backend`，项目文档放在 `docs`。
2. 数据库迁移放在 `backend/migrations`，部署配置放在 `deploy` 或根目录明确位置，GitHub 配置放在 `.github`。
3. 未经批准不得改变一级目录结构；项目不需要的二级目录可以省略。
4. 不得提交临时文件、日志、数据库文件和真实业务数据。

本项目保持 `web-prototype`、`web_backend`、`return_analysis`、`return_semantics` 等现有结构和兼容性，不为套用模板重命名目录或全量重构。

前端业务页面、组件和 Hook 优先集中到已有 `web-prototype/src/features/<业务域>`，跨业务请求继续复用 `shared/api` 的领域 API 与公共请求入口。后端按业务职责整理现有路由和服务，不为凑目录建立空壳 Repository。同一业务域前后端命名应可对应，便于顺序追踪页面、请求、路由和服务。

## 3. 既有项目规范接入

项目已有规则或贡献指南时，不得用公司模板整文件覆盖。公司规范是默认基线，已验证的业务、架构和工具约束以项目事实为准。接入属于非简单任务，必须先完成审计并获得确认。

### 3.1 只读审计

修改规则前必须：

1. 读取根目录及相关子目录的 `AGENTS.md`，确认作用域，并检查 `AGENTS.override.md`、README、贡献指南和专项规范。
2. 从代码、配置和自动化入口核对技术栈、目录、启动、检查和部署方式。
3. 将现有规则分为保留、重复、疑似过时、冲突、目录特有、低频专项和公司规范缺失。
4. 说明修改文件、合并方式、风险和验证方法；无法确认的规则保持不变并请求确认。

### 3.2 分类与合并

| 规则类型 | 处理方式 |
| --- | --- |
| 项目业务事实、架构边界、禁止事项和真实检查命令 | 保留，并以项目实际情况为准 |
| 与公司规范含义相同的规则 | 只保留一个事实来源，删除重复表述 |
| 已由项目工具稳定强制执行的格式和静态规则 | 保留工具、配置和执行命令，不在始终加载的文件中逐条复述 |
| 只影响一个目录的规则 | 放入该目录已有或必要的嵌套 `AGENTS.md`，不得在根文件重复 |
| 低频或任务专项流程 | 放入现有专项文档，并在根文件说明准确的读取条件 |
| 有证据确认已经失效的规则 | 说明证据和影响后删除 |
| 无法确认真伪的规则 | 保留并请求确认，不得自行删除 |
| 项目不使用的公司默认技术或流程 | 不复制，并在必要时记录为不适用或项目差异 |

合并时补充缺失的安全和生产底线，不得机械追加完整模板、改变已确认的技术栈或统一目录。

### 3.3 冲突处理

1. 法律合规、数据安全、权限、生产数据库、生产发布和破坏性操作采用更严格规则，不得通过项目差异放宽。
2. 项目实际技术栈、目录、包管理器、测试框架、部署方式和已验证设计系统优先于公司默认值。
3. 根规则与子目录规则冲突时，子目录规则只在其目录作用域内优先，并应明确说明例外原因。
4. 规则无法同时满足或证据不足时，列出双方规则、项目证据、影响和建议，获得确认后处理。

### 3.4 规则文件边界

父级规则与路径上的子级规则累积生效。嵌套 `AGENTS.md` 只补充目录特有约束，不重复父级规则；只有目录确有独立命令、架构或安全约束时才创建。

同一目录存在 `AGENTS.override.md` 时，Codex 不加载同目录的普通 `AGENTS.md`。该文件只用于明确的替换场景，不得用来追加公司规则；未经确认不得新增、删除或替换。

全局 `AGENTS.md` 只保存跨项目偏好和底线；业务、架构、检查和安全规则须随仓库维护。

普通 Markdown 文件不会自动加入规则链。根文件须用“触发条件 + 路径”建立索引；已有等价文档时直接索引，未同步的专项规范不得保留索引。

### 3.5 规模、版本与升级

新项目根目录 `AGENTS.md` 以 100 行以内为目标。现有项目超出目标时，先删除重复和失效内容，再按作用域和加载频率渐进迁移；不得仅因行数删除有效规则或阻塞必要修改。

Codex 当前默认最多组合 32 KiB 项目规则。接近限制时，减少重复、缩小始终加载范围或按目录分层，不得用提高限制代替治理。加载行为以 [Codex 官方说明](https://developers.openai.com/zh-Hans/docs/agent-configuration/agents-md) 为准。

升级时将变更分为适用、不适用、已存在和冲突，只合并适用且缺失的内容，再更新项目记录的基线版本。

规范发布时，发布提交、README 版本、CHANGELOG 版本和 `vMAJOR.MINOR.PATCH` 标签必须一致，并确认 GitHub 标签 ZIP 可访问。没有匹配标签和可访问版本包时，不得将该版本报告为已完成发布。

当前项目根目录已有 `README.md`，其中的环境、启动、检查和部署说明必须与 `pyproject.toml`、`web-prototype/package.json`、`scripts/quality.py`、`compose.yaml`、`Dockerfile`、`Caddyfile` 和 `docs/architecture/README.md` 保持一致；事实冲突时以实际配置和代码为准，并同步修正 README。

### 3.6 规范接入控制

使用者接入规范不需要 Git，正式开发仍应使用 Git 或其他受控版本管理。没有 Git 时，不得报告已经提交、推送或具备可靠回滚能力。

Codex 接入或升级规范时按以下顺序执行：

1. 确认当前目录是新建或已有业务项目的根目录，检查网络、写入权限、Git 状态、现有规则和回退条件。
2. 优先通过 HTTPS 获取已发布版本的标签 ZIP；无法取得时先说明原因并确认是否使用同版本的受控离线 ZIP，只有用户明确要求试用主分支时才使用 `main.zip`。
3. 将 ZIP 下载并解压到业务项目之外的临时目录，核对来源和版本后，只读审计规范与目标项目。
4. 用通俗语言说明当前阶段、准备执行的操作、影响和需要用户决定的事项；修改前列出目标文件、风险、恢复方式和验证方法。
5. 获得确认后再修改。没有 Git 的现有项目须先将目标规则文件备份到项目外，并说明恢复位置和方法；临时备份不能代替版本管理。
6. 新项目只复制适用的 `AGENTS.md`、`docs/codex` 和必要模板；现有项目差异合并，不得覆盖有效规则或将完整规范仓库嵌套到业务项目。
7. 接入后新建 Codex 任务，从项目根目录报告实际加载的 `AGENTS.md` 路径和关键规则，并检查所有索引路径以及 `AGENTS.override.md` 的影响。
8. 在项目 README 记录规范基线版本、接入来源、接入日期、版本控制状态、加载验证和项目差异。

出现以下情况时停止接入并请求处理：无法确认项目根目录，规范来源或版本无法核对，现有规则冲突且无权决定，已有规则文件需要修改但既无版本控制也无法备份，或者操作涉及无权处理的敏感数据、权限和生产环境。

## 4. 分层 AI 协作开发流程

流程产物可以是对话、图示或任务说明；只有用户要求或项目确有持久化需要时才写入文档。不得为满足流程机械产生无用文档。

### 4.1 任务分级

| 级别 | 判定 | 必要流程 |
| --- | --- | --- |
| 简单 | 现有模式内的局部修改，不新增业务规则、数据、接口或高风险影响 | 目标、验收、影响、修改和检查 |
| 标准 | 新页面、接口、数据字段或业务操作 | 需求定义、必要设计、验证策略、真实闭环和验收 |
| 高风险 | 新系统、跨系统流程、敏感数据、认证权限、数据迁移、不可逆操作、明确容量要求或部署变更 | 标准流程，加安全、隐私、容量、迁移、监控、发布和回滚设计 |

AI 须选择能覆盖风险的最轻级别并说明理由；无法判定时按更高一级处理并请求确认。

### 4.2 完整生命周期与确认门

| 阶段 | 核心产物 | 通过条件 |
| --- | --- | --- |
| 发现问题 | 真实问题、现状、用户、约束和改进价值 | 确定值得解决 |
| 定义需求 | 目标、范围、不做事项、成功指标和验收标准 | 用户确认需求 |
| 业务与产品设计 | 业务、用户、数据、页面、系统和权限方案 | 关键规则和目标流程已确认 |
| 原型与可行性验证 | 前端 Demo、技术验证或直接实现决策 | 最大不确定性已降低 |
| 技术与任务计划 | 修改范围、顺序、风险、回滚和验证方案 | 非简单任务获得实施确认 |
| 增量开发 | 先打通最小真实闭环，再扩展功能 | 代码、数据和交互一致 |
| 综合验证 | 技术检查、用户验收和风险结果 | 达到交付条件 |
| 发布、运营与改进 | 发布记录、监控、反馈、效果判断和后续动作 | 达标、改进、回滚、暂停或下线决策明确 |

### 4.3 从现有做法到目标系统

用户描述的现有操作是理解问题的证据，不是默认的系统方案。标准和高风险任务必须：

1. 记录现状流程 `As-Is`，逐步追问目的、输入、输出、角色和异常。
2. 将每个步骤区分为必须保留的业务规则、法律或组织硬约束、现有工具的限制和补救动作、可调整的操作习惯。
3. 用 Web 系统能力重新设计目标流程 `To-Be`，不得机械复制导出、复制、重复录入和人工传话等旧工具限制。
4. 对保留、变更和删除的步骤说明理由，获得用户确认后再进入详细设计。

### 4.4 设计视角

| 视角 | 必须回答 |
| --- | --- |
| 目标与范围 | 为谁解决什么问题，什么结果算成功，明确不做什么 |
| 参与者与职责 | 谁使用、审批、维护或提供外部能力 |
| 业务流程与规则 | 业务如何触发、流转、变更状态和处理异常 |
| 用户旅程与操作 | 用户从哪里进入、做什么、得到什么反馈 |
| 领域与数据 | 核心对象、唯一事实源、状态、来源、去向和生命周期 |
| 信息架构与页面 | 导航、页面关系、字段、操作和各类页面状态 |
| 系统与接口 | 前后端职责、接口、外部集成、事件、定时任务和失败边界 |
| 验收与度量 | 功能如何验收，业务效果如何度量，何时复查并采取什么动作 |

安全、隐私、权限、审计、可访问性、性能、可用性、容量、兼容性、成本、许可证和维护能力是横跨各视角的约束；只展开与当前任务有关的内容。

### 4.5 原型、技术验证与真实闭环

1. 按最大不确定性选择前端 Demo、技术验证或直接实现，不得因为 Demo 直观就忽略更高的集成、数据或安全风险。
2. 新系统、新流程、多角色交互或界面不确定性高时，优先使用足以验证操作流程的 Demo。
3. 原型只需验证高风险假设，不默认是生产代码，也不代表功能完成。
4. Demo 确认后必须先定义数据和接口契约，打通一个包含真实页面、接口、业务逻辑和数据读写的最小端到端流程，再扩展其他功能。

### 4.6 PDCA 闭环

1. `Plan`：记录改造前基线、目标、验收标准、可量化指标、数据来源、负责人和复查时间；不适用时说明理由。
2. `Do`：执行验证、开发和发布，保留与目标和方案对应的可验证结果。
3. `Check`：对照验收标准、用户反馈和业务指标检查技术结果与实际效果。
4. `Act`：根据证据明确保留、优化、回滚、暂停或下线，并将未解决问题进入下一轮计划。

简单任务以验收标准完成最小 PDCA；有可观测业务效果的功能必须说明上线后如何复查。

## 5. 开始开发前

修改代码前必须：

1. 按 `AGENTS.md` 索引读取相关专项规范，并阅读 README、需求、相关代码和测试。
2. 判定任务级别，检查调用链、现有实现和可复用能力。
3. 检查 README 的可选开发辅助资源是否命中当前问题。命中且尚未配置时，说明解决的问题、适用原因、来源、许可证或权限风险、配置变化和不配置时的处理方式，同一任务只询问一次；未获确认不得安装或修改个人、项目配置。
4. 对非简单且可能已有通用解法的需求，可以只读调研开源项目，并记录候选方案、来源、许可证、维护状态、安全风险、适配范围和集成成本。
5. 复述已确认的需求、目标流程、验收标准和不做事项。
6. 列出修改文件、影响内容及数据库、认证、权限、配置、依赖和部署影响。
7. 说明风险、回滚方式和验证方案，非简单任务获得确认后再修改。

开源调研只用于需求讨论和方案比较。复制代码、引入依赖或改变技术方案前，必须说明来源与影响，并按本规范获得确认。

涉及 Web 界面时，还须读取 `docs/codex/frontend.md` 和 `docs/web-ui-standard.md`，再按核心规范中的触发条件读取布局、表单或数据专项规范。检查已有令牌、组件、布局和相似页面，明确设计来源、目标视口及页面状态；不得将公司新项目组件基线套入本项目。

## 6. 修改范围

必须：

1. 只修改完成当前任务所必需的文件，保持现有业务规则、接口和兼容性。
2. 复用已有代码和实现模式，新增或修改业务逻辑时补充必要测试。
3. 发现无关问题时只记录，不顺带修改。

不得：

1. 增加需求外的功能、页面、接口、业务规则或字段。
2. 进行与当前任务无关的重构或修改无关文件。
3. 擅自删除功能、接口、字段或数据，或修改公共模块、认证、权限和部署配置。
4. 为“以后可能使用”提前增加代码、字段或组件。
5. 在多处维护同一业务规则。

## 7. 安全与生产边界

不得主动读取、生成、提交、输出或传播：

- 真实密码、Token、AccessKey、SecretKey 和私钥。
- 生产环境变量的真实值。
- 未脱敏的真实业务数据。
- 包含真实敏感信息的数据库文件、日志、上传文件和导出结果。

可以读取和处理：

- 认证相关的代码、字段名和配置结构。
- 不包含真实凭据的 `.env.example` 和占位值。
- 测试数据、模拟数据和已经脱敏的数据。
- 用户明确提供且不包含真实敏感信息的需求附件、示例文件和设计资料。

允许使用不显示命中值的自动化工具扫描源码和提交记录。意外发现真实敏感信息时，应停止处理相关内容并提醒用户，不得在日志或回复中复述其值。不得直接修改生产数据库或自动执行生产迁移；生产操作只能由部署负责人执行。

## 8. 项目文档

创建或维护项目时，README 至少包含：

- 项目用途、适用范围和明确不做的事项。
- 技术栈、系统架构和关键业务规则。
- 本地启动、测试和构建方式。
- 部署文档入口。

根目录 `AGENTS.md` 至少包含业务边界、Codex 修改规则、禁止修改内容、专项规范索引、必须执行的检查以及数据和 Git 安全要求。重要业务规则不得只存在于聊天记录或个人记忆中。
