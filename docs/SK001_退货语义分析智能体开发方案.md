# SK001 退货语义分析智能体开发方案

## 1. 项目目标

针对 `SEEKWAY:US` 店铺、`SK001` Listing 的 Amazon 退货数据，结合客户评论、Amazon reason、SKU 产品关系和 Listing 承诺，完成可追溯的多标签退货语义分类。

首版交付形式为本地离线批处理程序，不建设 Web 系统，不建设可自主调用工具的复杂 Agent。

系统需要输出：

- 评论中的问题标签、正面标签和主要退货原因。
- 每个语义结论对应的原文证据。
- 问题涉及的产品部位和属性。
- 与 Listing 承诺的关系。
- 自动通过、二次验证、人工复核或未知语义状态。
- 标签分布、SKU 分布和业务汇总结果。

## 2. 市场方案调研结论

### 2.1 方案对比

| 方案 | 可借鉴能力 | 不直接采用的原因 |
| --- | --- | --- |
| AWS Comprehend Custom | 多标签分类、批量推理、置信分数、分类指标 | 依赖已标注数据，主要输出标签，无法直接满足证据、部位、主因和 Listing 承诺判断 |
| Azure Language / Foundry | 观点挖掘、自定义多标签分类 | 观点挖掘与业务分类相对分离，旧版自定义文本分类将在 2029 年退役 |
| Vertex AI + Gemini | JSON Schema 约束、批量推理、模型评测 | 云资源配置和平台成本较高，对当前数据规模没有明显收益 |
| Thematic、Chattermill | 自动发现主题、人工调整主题体系、结果追溯 | 偏通用 VOC 平台，难以完整实现本项目的业务标签和证据规则 |
| DeepSeek + Python | 语义灵活、成本低、业务规则完全可控 | 需要自行实现校验、评测、缓存和人工复核机制 |

### 2.2 技术决策

采用 `DeepSeek + Python` 的混合语义决策流水线，并吸收市场方案中的以下设计：

- 分类体系独立配置和版本化。
- 每条结果能够追溯到评论原文。
- 固定标签分类和未知主题发现并存。
- 模型结果必须经过程序校验。
- 人工修正持续沉淀为评测和训练数据。

## 3. 设计原则

1. 评论是主要语义证据，Amazon reason 是弱证据。
2. 先抽取语义事实，再映射业务标签。
3. 空评论不推测具体问题。
4. 产品信息只能用于评估，不能创造客户没有表达的问题。
5. 允许一条评论包含多个问题标签和多个正面标签。
6. 主要退货原因只能来自问题标签，允许为空或并列。
7. 模型只负责语义理解，程序负责数据关联、约束、校验和输出。
8. 无法稳定判断的评论进入人工复核，不强制分类。
9. 分类体系无法覆盖的语义进入未知语义池，不统一塞入“其他”。

## 4. 总体架构

```text
Amazon 退货数据
    ↓
SK001 产品关系精确筛选
    ↓
评论清洗、空评论识别、重复评论合并
    ↓
DeepSeek 结构化语义抽取
    ↓
业务标签映射
    ↓
Python 证据和业务规则校验
    ├── 自动通过
    ├── 二次模型验证
    ├── 人工复核
    └── 未知语义池
    ↓
Excel 明细和统计结果
    ↓
人工修正样本回流
```

该系统对外可称为“退货语义分析智能体”，内部实现为受控状态机。模型不能自主修改业务标签、产品数据或分类规则。

## 6. 语义数据结构

模型先输出原子语义单元，再输出业务标签映射。

```json
{
  "semantic_units": [
    {
      "subject": "PRODUCT",
      "aspect": "HEEL",
      "category": "FIT",
      "opinion": "slides off",
      "sentiment": "NEGATIVE",
      "assertion": "AFFIRMED",
      "implicit": false,
      "evidence": "slides off my heel"
    }
  ],
  "problem_labels": ["后跟不跟脚"],
  "positive_labels": [],
  "primary_labels": ["后跟不跟脚"],
  "needs_review": false,
  "review_reasons": []
}
```

### 6.1 语义字段

| 字段 | 作用 |
| --- | --- |
| `subject` | 区分产品、客户、物流或其他对象 |
| `aspect` | 表示鞋跟、鞋口、鞋底、鞋面、尺码等部位或属性 |
| `category` | 表示尺码、舒适性、防滑、质量、外观等问题类别 |
| `opinion` | 对客户观点进行简短标准化 |
| `sentiment` | 正面、负面或中性 |
| `assertion` | 已确认、否定或不确定表达 |
| `implicit` | 是否需要结合上下文推导隐含观点 |
| `evidence` | 评论中的连续原文证据 |

## 7. 语义处理规则

### 7.1 一词多义

模型必须结合对象、动作和上下文理解词义。例如：

- `slip on easily`：穿脱方便。
- `slip on wet rocks`：湿滑环境防滑问题。
- `slip off my heels`：后跟不跟脚。

### 7.2 多问题评论

评论包含多个问题时全部保留，例如：

```text
tight around the opening but loose at the heel
```

应识别为鞋口偏紧和后跟偏松两个问题，不合并成笼统的尺码问题。

### 7.3 否定和反向表达

`not too tight`、`didn't feel slippery` 等表达不能生成对应的负面问题标签。

### 7.4 隐含观点

`wanted more support` 可以标准化为支撑不足，但必须保留原文证据，并标记 `implicit = true`。隐含观点默认进入二次验证或人工复核，直到积累足够的稳定样本。

### 7.5 证据约束

- `evidence` 必须是原评论中的连续子串。
- 找不到证据时不能自动通过。
- Listing、Amazon reason 和产品特征不能作为评论语义证据。

### 7.6 主因约束

- `primary_labels` 必须是 `problem_labels` 的子集。
- 正面标签不能成为主因。
- 没有明确主因时允许为空。
- 两个问题同等重要时允许并列主因。

## 8. 决策分流

不采用模型自报置信度。系统根据可验证条件决定处理状态。

### 8.1 自动通过

同时满足以下条件：

- 模型输出通过结构校验。
- 标签属于当前分类体系。
- 原文证据校验通过。
- 不存在标签组合冲突。
- 不是无法解释的隐含语义。
- Amazon reason 冲突不影响当前结果，或不存在冲突。

### 8.2 二次模型验证

以下情况使用更强模型进行二次验证：

- 隐含观点。
- 一词多义。
- 多个相反问题并存。
- 主因不明确。
- 评论与 Amazon reason 明显冲突。

### 8.3 人工复核

以下情况直接进入人工复核：

- 两次模型判断不一致。
- 证据校验失败。
- 标签映射违反业务规则。
- 评论文本存在明显歧义或信息不足。

### 8.4 未知语义池

分类体系没有覆盖但评论表达清晰的问题进入未知语义池。未知语义按标准化观点聚合，定期判断：

- 是否为已有标签的表达变体。
- 是否需要新增标签。
- 是否只是低频、无业务价值的描述。

首版不引入向量数据库。未知语义达到一定数量后，再使用文本向量进行离线聚类。

## 9. 技术选型

| 技术 | 用途 |
| --- | --- |
| Python | 批处理程序和业务规则 |
| pandas | CSV、Excel 数据处理和关联 |
| openpyxl | Excel 格式化输出 |
| Pydantic v2 | 模型响应、配置和业务字段校验 |
| OpenAI Python SDK | 调用 DeepSeek 兼容接口 |
| JSONL | 推理缓存、断点续跑和人工修正记录 |
| pytest | 规则、数据关联和结果校验 |

模型策略：

- 普通评论使用 `deepseek-v4-flash` 非思考模式。
- 难例使用 `deepseek-v4-pro` 二次验证。
- 模型名称通过配置指定，不写死在业务代码中。
- 使用 JSON Output，随后由 Pydantic 进行结构和业务校验。
- 采用低随机性参数，保证批次结果尽量稳定。

首版不使用：

- LangChain 或 LangGraph。
- 多智能体框架。
- 向量数据库。
- Web 后台。
- 关系型数据库。
- 模型微调。

## 10. 代码结构

```text
return_semantics/
├── data.py
├── schemas.py
├── taxonomy.py
├── prompt.py
├── model_client.py
├── validator.py
├── pipeline.py
└── exporter.py

config/
├── taxonomy_water_shoes.json
└── listing_claims_sk001.json

scripts/
└── run_return_semantics.py

tests/
```

模块职责：

- `data.py`：读取数据、筛选 SK001、关联 MSKU、清洗评论和去重。
- `schemas.py`：定义模型输入输出和内部数据结构。
- `taxonomy.py`：加载并校验标签体系与 Listing 承诺配置。
- `prompt.py`：构建系统提示、标签定义和少量示例。
- `model_client.py`：封装 DeepSeek 调用、重试、缓存和用量记录。
- `validator.py`：验证证据、标签、主因和冲突规则。
- `pipeline.py`：组织完整批处理流程和决策分流。
- `exporter.py`：输出 Excel 明细和统计结果。
- `run_return_semantics.py`：提供通用退货语义分类命令行入口。

## 11. 金标准与评测

### 11.1 金标准集

从有效评论中抽取 500 条人工标注样本：

- 300 条用于提示设计、错误分析和规则校准。
- 200 条作为不可见验收集，在最终验收前不参与提示修改。

抽样需要覆盖：

- 高频 Amazon reason。
- 长短评论。
- 多问题评论。
- 否定和比较表达。
- 隐含观点。
- 评论与 Amazon reason 冲突。
- 信息不足和未知语义。

### 11.2 对比基线

至少比较两种方法：

1. 评论直接映射业务标签。
2. 先抽取结构化语义，再映射业务标签。

只有第二种方法在验收集上确实更好时，才作为正式方案。

### 11.3 评测指标

- Micro Precision、Recall、F1。
- Macro Precision、Recall、F1。
- 多标签集合完全匹配率。
- 主因准确率。
- 证据原文匹配通过率。
- 自动通过精度和覆盖率。
- 人工复核比例。
- 未知语义识别数量。

自动通过结果的人工抽检精度目标不低于 95%。不为了降低人工复核比例而放宽自动通过条件。

## 12. 输出文件

最终 Excel 至少包含以下 Sheet：

| Sheet | 内容 |
| --- | --- |
| 分类明细 | 每条退货记录的最终标签、主因和状态 |
| 语义单元 | 每条评论拆分后的部位、观点、情感和证据 |
| 人工复核 | 需要业务人员确认的评论和复核原因 |
| 未知语义 | 分类体系未覆盖的标准化语义 |
| 标签统计 | 标签、SKU、ASIN、Amazon reason 等维度统计 |

所有结果保留：

- 原始记录标识。
- 原评论。
- 原始 Amazon reason。
- 模型和提示版本。
- 分类体系版本。
- 处理时间。
- 自动通过或复核原因。

## 14. 验收标准

1. SK001 产品范围筛选准确，不混入其他 Listing。
2. 原始记录数量、去重评论数量和输出数量能够对账。
3. 模型响应经过结构校验后才能进入正式结果。
4. 正式标签全部属于当前分类体系。
5. 证据字段能够在原评论中找到。
6. 主因标签满足业务约束。
7. 空评论不生成具体语义问题。
8. 自动通过结果人工抽检精度不低于 95%。
9. 人工复核和未知语义能够单独导出。
10. 同一输入、同一模型和同一配置可以重复运行并复用缓存。

## 15. 主要风险

| 风险 | 处理方式 |
| --- | --- |
| 隐含观点误判 | 标记隐含性，进入二次验证或人工复核 |
| Amazon reason 污染评论理解 | 第一阶段不向模型提供 Amazon reason |
| Listing 信息诱导模型 | 评论语义抽取后再处理 Listing 承诺关系 |
| 长尾标签样本不足 | 关注每个标签的 Macro F1，保留未知语义池 |
| API 中断或返回空内容 | 本地缓存、有限重试和断点续跑 |
| 提示或模型升级导致结果漂移 | 保存模型、提示、分类体系和运行版本 |
