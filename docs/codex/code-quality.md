# Codex 代码质量与拆分规范

当任务新增、修改、重构或评审代码时，必须读取本文件。规则适用于所有进入仓库的代码。
## 1. 设计原则

1. 保持高内聚、低耦合，每个模块只承担清晰且相关的职责。
2. 保持依赖方向清晰，避免循环依赖和跨层调用。
3. 优先保证代码可读性，使用准确命名和简单控制流程。
4. 控制函数、类和组件的职责范围，复杂逻辑必须合理拆分。
5. 隐藏模块内部实现，仅暴露完成协作所需的最小接口。
6. 避免重复业务规则，但不得为了复用而过早抽象。
7. 优先遵循项目已有结构和实现方式，保持代码风格一致。
8. 代码设计必须便于测试、修改和问题定位。
9. 不得硬编码密码、密钥、服务地址、端口、文件路径和环境相关参数，应通过配置或环境变量管理。
10. 业务状态、类型、阈值和重复使用的固定值应定义为具名常量、枚举或集中配置，不得散落在代码中。
11. 仅当值含义明确、不会随环境或业务变化且只在局部使用时，才允许直接使用字面量。
12. 文件包含多个能够独立变化的职责，或已经影响理解、定位、测试和修改时，必须按业务边界拆分。
13. 拆分后必须保持依赖方向清晰和对外接口稳定，不得引入循环依赖、重复逻辑或无业务收益的文件碎片。
14. 维护历史长文件时只处理与当前需求相关的部分；大范围拆分必须先说明范围、收益和风险并获得确认。

## 2. 规模、复杂度与拆分

可维护性以职责聚合、依赖方向、复杂度、可分析性、可修改性和可测试性为主要依据。代码行数只能作为预警信号，不得单独作为质量结论或任务完成条件。

1. 模块、类、组件和函数存在多个能够独立变化的职责时，应按业务边界拆分。
2. 文件超过 500 行时必须检查职责数量、依赖关系、复杂度和测试方式；仅有行数较多不得作为强制拆分理由。
3. 文件超过 800 行时，必须在实施方案中说明当前职责、复杂逻辑位置、拆分可行性和测试影响。
4. 新文件预计超过 1000 行，或本次修改使原本不超过 1000 行的文件跨过 1000 行时，必须在实施前提出拆分方案；确实不宜拆分时，说明原因并获得确认。
5. 已有超长文件不阻塞局部缺陷修复和必要变更；本次修改不得继续加入无关职责，能够独立的新能力应放入职责明确的模块。
6. 函数只完成一个明确目标。函数超过 50 行时必须检查复杂度和职责，不得仅为减少行数提取无业务含义的辅助函数。
7. 函数默认阈值：圈复杂度不超过 10、分支数不超过 12、语句数不超过 50、嵌套块不超过 5、位置参数不超过 5；项目已有认知复杂度检查时默认不超过 15。
8. 超过函数质量阈值时必须优先简化控制流程、拆分职责或调整数据结构；确有合理原因无法降低时，必须在实施方案和完成报告中说明。
9. React 页面和组件应按数据获取、业务状态、表单、弹窗、表格配置和独立页面区域检查职责；即使行数较少，混合多个独立职责时也必须拆分。
10. 自定义 Hook 只封装一组内聚且可复用的状态或副作用，不得通过把复杂逻辑整体搬入 Hook 来规避组件复杂度。
11. Router、Service、Repository 和展示组件必须保持职责边界，不得为了缩短文件而增加无业务意义的转发层。
12. 拆分后不得产生循环依赖、重复业务规则、只转发调用的空壳模块、过度参数传递或难以追踪的文件碎片。
13. 一个任务或代码评审应保持为一个自包含目标。本次变更量（新增和修改，不含纯删除）接近或超过 1000 行时，必须优先拆分为可独立验证的阶段；无法拆分时应在实施前说明原因并获得确认。
14. 功能修改与大范围重构原则上分开实施；只有重构是完成需求的必要前提时才可纳入同一任务，并必须说明范围和回归风险。
15. 采用渐进治理：新增和修改的代码不得降低整体代码健康度，不要求为局部需求一次性重构全部遗留代码。
16. 完成修改后必须检查本次涉及文件的职责、规模和函数复杂度，并报告触发的预警、处理结果和未处理原因。

## 3. 注释与清理

注释应解释业务规则、设计原因、边界条件、特殊处理、兼容性要求和风险原因，不得简单重复代码含义。

完成任务后必须：

1. 检查本次新增代码是否重复已有实现。
2. 删除因本次修改而失效的旧代码。
3. 删除不再使用的 import、export、函数、组件和依赖。
4. 不得为了兼容“可能未来使用”的逻辑保留无实际用途的代码。
5. 使用项目已有工具检查代码重复、死代码和循环依赖；缺少工具时进行人工检查并如实报告。
